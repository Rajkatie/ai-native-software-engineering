# ADR-001: Architectural Foundation

**Status:** Accepted

## Context

This project is intended to demonstrate an AI-Native Software Development Lifecycle while building a real software system.

The software system must have a clear architectural foundation so that AI agents are not free to generate code without architectural constraints.

We will use Clean Architecture principles as the foundation for the software system.

The architecture must also be understandable and enforceable by AI agents and automated verification mechanisms.

## Decision

We will use **Clean Architecture** as the architectural foundation of the software system.

The architecture will follow the Dependency Rule:

> Source-code dependencies must point inward toward higher-level policies.

The system will be organized around the following conceptual boundaries:

### Domain / Entities

Contains enterprise business rules and domain concepts.

The Domain must not depend on:

* UI
* Database
* Web frameworks
* AI frameworks
* Infrastructure
* External services

### Application / Use Cases

Contains application-specific business rules and use cases.

Use Cases orchestrate the application flow and interact with the Domain.

Use Cases must remain independent of external implementation details.

Where communication with an outer layer is required, boundaries/interfaces will be defined toward the inner architecture and implemented by outer layers.

### Interface Adapters

Contains adapters that translate between external representations and the formats used by the application.

Examples include:

* Controllers
* Presenters
* View Models
* Request/Response models
* Persistence adapters

### Frameworks and Infrastructure

Contains implementation details and external mechanisms such as:

* ASP.NET Core
* Database
* Entity Framework Core
* External APIs
* AI/LLM providers
* Agent frameworks
* Messaging infrastructure

These components must remain at the outer boundary of the system.

## AI-Agent Constraint

AI agents participating in development must treat the Clean Architecture boundaries as **architectural constraints**, not suggestions.

An agent must not introduce a dependency that violates the Dependency Rule merely because the implementation is convenient.

For example:

```text
Domain → Infrastructure
Domain → Entity Framework Core
Domain → ASP.NET Core
Use Case → Controller
Use Case → Database implementation
```

are architectural violations.

## Verification

Architectural rules must eventually be represented as executable verification rules wherever practical.

The project will progressively introduce automated checks that verify:

* Dependency direction
* Layer boundaries
* Forbidden dependencies
* Testability of business rules
* Compliance with approved specifications

An AI agent reporting that a task is complete will not be considered sufficient evidence of architectural compliance.

## Consequences

### Positive

* The software remains independent of frameworks and infrastructure.
* Business rules remain testable.
* AI-generated code operates within explicit architectural boundaries.
* Architectural violations can become machine-verifiable.
* The architecture provides a stable foundation while implementation technologies evolve.

### Negative

* The architecture introduces additional abstractions and boundaries.
* AI agents require additional context and constraints to work effectively.
* Some simple implementations may require more structure than a conventional layered application.
* Architectural verification becomes an additional engineering responsibility.

## Relationship to the AI-Native SDLC

Clean Architecture defines **how the software system is structured**.

The AI-Native SDLC defines **how the software is engineered**.

These are intentionally treated as separate concerns.

The AI-Native SDLC will use specifications, governance, agents, verification, human approval, and feedback to build and evolve software that conforms to this architectural foundation.
